================================================================================
PROBLEM
================================================================================

A critical race condition in the PromptMuse Free Plan activation allowed users
to create multiple concurrent active subscriptions, breaking billing consistency.

Race Scenario:
- User sends two simultaneous Free Plan activation requests
- Both requests pass the existence check (no active subscription found yet)
- Both create new Subscription documents
- MongoDB accepts both (no unique constraint)
- User ends up with 2 active subscriptions
- Billing system shows inconsistent information

Root Cause:
- No unique database index on (userId, status='active')
- Check-then-create pattern was not atomic
- No application-level error handling for duplicate keys

================================================================================
SOLUTION
================================================================================

Two-layered protection implemented:

LAYER 1: DATABASE CONSTRAINT (Primary)
- Added unique partial index on (userId, status='active')
- MongoDB now rejects any second active subscription per user
- Index name: unique_active_subscription_per_user
- Partial filter expression: { status: 'active' }

LAYER 2: APPLICATION IDEMPOTENCY (Fallback)
- Enhanced error handling in activateFreeSubscription()
- Catches MongoDB E11000 (duplicate key) errors
- Returns winner's subscription on collision
- Both concurrent requests get same subscription ID

Result: Concurrent activations are now idempotent and safe.

HOW IT WORKS
================================================================================

CONCURRENT REQUEST A & B ARRIVE SIMULTANEOUSLY:

Request A:
  1. Query existing subscription → null
  2. Plan validation → pass
  3. Create new Subscription object
  4. Call subscription.save()
  5. MongoDB: Insert operation
     → First write succeeds (index allows it)
     → Document created with {userId: X, status: 'active'}
  6. Return subscription A to frontend ✅

Request B:
  1. Query existing subscription → null (B started before A's write)
  2. Plan validation → pass
  3. Create new Subscription object
  4. Call subscription.save()
  5. MongoDB: Insert operation
     → E11000 duplicate key error (unique index rejects)
  6. Catch error handler activates
     → Query for existing active subscription
     → Find subscription A (created by Request A)
  7. Return subscription A to frontend ✅

RESULT: Both requests receive SAME subscription ID
        No duplicates created
        Billing is consistent ✅
