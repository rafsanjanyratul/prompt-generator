   Both use getCreditBalance() from same endpoint. Independent loads
   acceptable for read-only data. Slight staleness is fine.

3. ✅ Usage & Credit History API Integration
   Both use isMounted pattern, proper error handling, actual backend
   response fields verified (payload.usage, payload.history).

4. ✅ Authentication Protection
   Billing, Checkout, History routes wrapped with ProtectedRoute.
   Pricing route is public. All working correctly.

5. ✅ Backend Response Fields vs Frontend
   No hallucinated fields. All rendered fields exist in responses.
   Defensive rendering with Array.isArray() checks.

6. ✅ Demo Payment Clearly Labeled
   4 locations: Pricing cards, Checkout confirmation, Success page,
   Failure page. User cannot confuse demo with real payment.

7. ✅ No Frontend Payment Control
   Frontend sends only planId for initiate, only paymentId for verify.
   Price and outcome 100% controlled by backend.

8. ✅ Duplicate Payment Prevention
   Button disabled during isProcessing. Retry only on failure.
   Error recovery requires navigation back to pricing.

   Added isMounted cleanup pattern to Header useEffect to prevent
   stale state updates after component unmount.

    Changed fallback from '0' to '—' so unavailable balance is not
    confused with depleted balance.
